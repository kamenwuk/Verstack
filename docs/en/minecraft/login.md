# Login

The Login phase is the step after Handshake where the client states who it wants to be and the server verifies it and lets it into the game. The server reaches it via `nextState = Login` from Handshake; the client sends Login Start, followed by the encryption, compression, and Login Success exchange.

Today only the entry into the phase and Login Start parsing are implemented: the name and UUID are stored on the connection, but the server sends no reply yet. Encryption, compression, Login Success, and online-mode authentication are the next sub-steps; they are not here.

## Packet types

| Type | Role |
|---|---|
| `LoginStartPacket` | DTO — name, UUID |
| `LoginStartPacketParser` | Parser — Login Start payload → DTO |

The DTO is a `readonly struct` with two fields: `Username` (the string the client claimed) and `Uuid` (the `Uuid` type from Protocol, 16 bytes big-endian). The UUID the client sends is not final: in online mode the server replaces it with the Mojang UUID in Login Success. For now the server keeps what was sent.

The parser is a `static class` that reads the packet body via `PacketReader` (after the packet id, which the dispatcher consumes). No name validation: the parser reads an arbitrary string; length and character checks are online-mode semantics, not wire format.

## Wire format

```
Login Start (client → server):  [0x00][VarInt(len)][UTF-8 name][16 bytes UUID, BE]
                                  ↑ packet id 0x00 in the Login phase
```

Fields:

| Field | Type | Note |
|---|---|---|
| name | length-prefixed UTF-8 | max 16 characters per protocol |
| uuid | UUID (16 bytes big-endian) | generated by the client; not a dashed string |

The chat-signature fields (timestamp, public key, signature) that Login Start carried in 1.19.x are gone in 1.21.x — they moved to the Configuration phase. The packet is minimal: just name and UUID.

## What the server does

On `(Login, 0x00)` the dispatcher parses Login Start, stores the name and UUID in the connection's fields, and returns `Keep`. Routing details are in [Dispatcher](dispatcher.md). The server's reply (Encryption Request / Set Compression / Login Success) is not implemented, so the client stalls and closes on timeout — expected for this step, which verifies entry into the Login phase and correct parsing.
