# Диспетчер

Диспетчер — точка, где payload одного кадра превращается в реакцию сервера. Он читает packet id из начала payload и маршрутизирует по `(фаза, packet id)` к нужному действию. Это пер-соединениый объект: каждое соединение получает свой диспетчер со своей фазой.

Три типа несут эту ответственность: `SessionPhase`, `PacketDispatcher`, `PacketDispatcherFactory`.

## Фаза на соединение

`SessionPhase` — enum фаз протокола (`Handshake`, `Status`; `Login`, `Play` добавятся). Значения упорядочены так, что `default(SessionPhase) = Handshake`: свежесозданный диспетчер уже в стартовой фазе без явной инициализации.

Фаза — поле экземпляра диспетчера, изолированное между соединениями. Это единственное изменяемое состояние на соединение, и причина, по которой существует фабрика: нельзя шарить один handler между всеми клиентами — каждый идёт по своему пути Handshake → Status → (Login → Play). См. [контракт фабрики](../network/packet-handler.md).

## Фабрика

`PacketDispatcherFactory` хранит общие для всех соединений immutable-данные (статус сервера) и в `Create()` выдаёт свежий `PacketDispatcher` с собственной фазой. `TcpServer` вызывает `Create()` в accept-цикле на каждое соединение.

Диспетчер владеет `ArrayBufferWriter<byte>` как полем: одна аллокация буфера на соединение, переиспользуется между Status-кадрами через `Clear()`. Handler живёт столько же, сколько соединение; буфер — столько же, сколько handler.

## Маршрутизация

Диспетчер реализует `IPacketHandler.OnPacket`. Внутри:

1. Создаёт `PacketReader` над payload кадра.
2. Читает packet id (VarInt) — сам, не делегирует, потому что именно по нему свитчуется роутинг.
3. `switch (_phase, packetId)` выбирает действие.

Таблица маршрутов Status-фазы:

| Фаза | packet id | Действие | Вердикт |
|---|---|---|---|
| `Handshake` | `0x00` | `HandshakePacketParser.TryParse` → `_phase = Status` (при `nextState = Status`) | `Keep` (или `Disconnect`, если тело не парсится) |
| `Status` | `0x00` | `ServerStatusSerializer.Write` → framing → ответ | `Keep` |
| `Status` | `0x01` | Читает `long timestamp` → пишет Pong `[0x01][timestamp, BE]` → framing → ответ | `Keep` (или `Disconnect`, если нет timestamp) |

Всё остальное (нет packet id, неизвестный packet id, несоответствие фазе) — ветка по умолчанию: лог + `Disconnect`. `SessionLifetime` чтёт вердикт [после flush'а](../network/server-lifetime.md).

## Что рвёт, а что нет

Диспетчер рвёт соединение на кадры, которые нельзя обработать: кадр без packet id, тело Handshake/Ping, которое не парсится, или packet id, не предусмотренный текущей фазой. Это мусор — легитимный клиент их не пришлёт. Рвать сразу означает: клиент получает быстрый фидбэк, сервер не тратит циклы на продолжение диалога с кривым пиром.

`nextState = Login` — **исключение**: это валидный Handshake с не реализованным nextState. Рвать здесь = рвать валидных клиентов, которые хотят логиниться. Логируется, фаза остаётся Handshake, вердикт `Keep`. Следующий пакет от клиента всё равно уйдёт в default-ветку и порвёт соединение.

Pong пишется inline, без отдельного сериализатора: payload тривиален (`VarInt(0x01)` + 8 байт big-endian), заводить под него класс — серебряная пуля. Чтение Ping (одно поле `long timestamp`) тоже inline. Асимметрия с Status Response (там сериализатор есть) оправдана разной сложностью.
